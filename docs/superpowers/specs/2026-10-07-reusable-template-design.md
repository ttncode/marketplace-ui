# Reusable site template — design

Date: 2026-10-07
Status: approved in conversation, pending written-spec review

## Goal

Turn `marketplace-ui` from a pixel-perfect clone of mcpmarket.com into a template that
starts any new website quickly:

- **Marketplace / directory / landing sites** — top navigation, the layout the clone already has.
- **Management apps** — a sidebar dashboard, e.g. a tool that manages, creates and posts videos
  to TikTok and YouTube.
- **Both in one product** — a public site plus a signed-in app.

Every site made from the template is a fixed copy that an agent or a developer is free to
change or redesign. Improvements to shared components reach existing sites only when that
site chooses to pull them.

### Success criteria

1. A new site is created with GitHub "Use this template", and its brand, copy and colors are
   changed by editing `src/site.config.ts`, `src/content/` and `src/app/theme.css` only.
2. Light, dark and system themes work on every page with no flash of the wrong theme.
3. Any Next.js app can install a component with `npx shadcn add @ttn/<name>`, and an existing
   site upgrades a component by re-running the same command and reviewing the git diff.
4. No MCP Market name, logo, copy or captured asset ships on `main`.
5. `npm run check` passes, and CI also builds the registry.

### Non-goals

- No backend, database, CMS or real authentication. All data stays static TypeScript.
- No published npm package and no monorepo.
- No configuration flag that switches between layouts. A layout is chosen by keeping or
  deleting a route group.
- No end-to-end test suite.

## Branches

- `mcpmarket-clone` — created from `main` at `5f7c598`, frozen as the reference clone. Every
  route and component this design drops stays available there.
- `main` — restructured into the template through pull requests.
- The repository is marked as a GitHub template repository. "Use this template" copies only
  the default branch and starts the new repository with fresh history, so new sites get
  neither the clone branch nor old commits that contain MCP Market assets.

### Choosing layouts for a new site

| New project | Keep | Delete |
| --- | --- | --- |
| Marketplace, directory, landing page, blog | `(site)`, plus `(auth)` if it has accounts | `(dashboard)` |
| Internal tool, admin panel | `(dashboard)`, `(auth)` | `(site)` |
| SaaS product with a public site | all three | nothing |

Top navigation fits pages people browse or read, with about seven or fewer top-level sections.
A sidebar fits screens people work in repeatedly, with many or nested sections, behind sign-in.

## Config and content

`src/site.config.ts` exports one `site` object typed `satisfies SiteConfig`:
`name`, `url`, `description`, `logo { light, dark }`, `nav`, `dashboardNav`, `footer { columns, copyright }`,
`socials`. `src/app/layout.tsx` builds `metadata` (title template, Open Graph, favicons) from it,
so the brand name appears in one place.

`src/content/` exports typed data; the types live in `src/lib/types.ts` so blocks can import them
without touching content, and ship in the registry. Both live under `src/` so the `node --test "src/**/*.test.ts"`
glob and the `@/` alias reach them; both import types only, so tests can load them directly.

| Type | Fields |
| --- | --- |
| `Listing` | `slug`, `name`, `summary`, `icon`, `category`, `tags`, `stars?`, `author`, `about` (paragraphs), `features`, `useCases`, `faq` |
| `Category` | `slug`, `name`, `description` |
| `FaqItem` | `question`, `answer` |
| `DashboardData` | `stats`, `activity`, `videos` (`id`, `title`, `thumbnail`, `platforms`, `status`, `scheduledAt`) |

Legal pages are TSX fragments in `src/content/legal/`, rendered inside the legal-page prose
styles. No markdown library is added; listing bodies are arrays of paragraphs. Demo content is neutral and invented; none of it comes
from mcpmarket.com.

**Rule:** components never import `src/content/` or `src/site.config.ts`. Pages read config and content
and pass them to blocks as props. This lets a block move to another site without its data.

## Theming

- `globals.css` maps tokens to Tailwind colors in `@theme inline` (`--color-ink`, `--color-canvas`,
  `--color-surface`, …), so components write `text-ink`, `bg-canvas`, `border-ink/14` instead of
  hex or rgba values. Opacity modifiers replace the source's `rgba(10,10,10,a)` values.
- `src/app/theme.css` holds two token sets: `:root` (light, today's measured values) and `.dark`.
  Every `--design-*` token and every shadcn token has a value in both.
- Hardcoded colors are replaced by tokens: the dither dot colors in `.design-dither-static`,
  the white highlights inside shadows, and any hex value in a component.
- `--design-accent` and `--design-accent-foreground` are added and feed `--primary` and `--ring`.
  Their default is today's black and white, so the light theme looks unchanged.
- Fonts stay in `layout.tsx` via `next/font`.
- **Theme switching:** `system` (default), `light` or `dark`, stored in `localStorage` under
  `theme`. An inline script in `<head>` sets the `.dark` class before first paint; `<html>` gets
  `suppressHydrationWarning` and loses its hardcoded `light` class. No dependency is added.
  In `system` mode the page follows `prefers-color-scheme` changes live.
- **Hero dither shader:** WebGL cannot read CSS variables, so `HeroDitherShader` reads the
  token colors with `getComputedStyle` and re-renders when the `.dark` class changes.
- `theme-toggle` is a block: a menu with System, Light and Dark, used in `site-header`
  and `app-topbar`.

## Registry

- `registry.json` uses the shadcn registry schema. Item types: `registry:ui` for `ui/`,
  `registry:block` for `blocks/` and `layout/`, `registry:file` for the theme
  (`theme.css` shipped as a `registry:file` with a target path, so it has one source), `registry:lib` for `utils` and the theme script.
  Items declare `dependencies` (npm) and `registryDependencies` (`@ttn/…`).
- `npm run registry:build` runs `shadcn build`, writing `public/r/*.json`. The template's own
  Vercel deployment serves the registry at `https://<template-domain>/r/{name}.json`.
- A consuming app adds to its `components.json`:
  `"registries": { "@ttn": "https://<template-domain>/r/{name}.json" }`
  and installs with `npx shadcn add @ttn/listing-card`.
- **Upgrade workflow:** in an existing site, re-run `npx shadcn add @ttn/<name> --overwrite`,
  review `git diff`, keep local changes that matter, commit. A block a site has redesigned
  heavily is owned by that site and stops taking upgrades.

## Agent guide

`AGENTS.md` is rewritten for the template (the Next.js agent-rules block stays as generated):

- Map: brand in `src/site.config.ts`, copy in `src/content/`, look in `theme.css`, sections in
  `blocks/`, primitives in `ui/`, shells in `layout/`.
- New-site checklist: choose route groups, edit config, replace content, set accent and fonts,
  replace `public/brand/`, update README.
- Rules: blocks take props and never import content; colors come only from tokens, defined for
  light and dark; no hex values in components; TypeScript strict, no `any`; named exports.
- Redesign ladder: change tokens first, then edit a block, then write a new block.
- Registry: a changed or added block updates its `registry.json` entry in the same commit.

The clone rule "match the source site 1:1" and the `toSiteHref` rule are removed.
README is rewritten to describe the template, the layout choice table and the registry.

## Testing

Unit tests run with `node --test`, as today:

- **No hardcoded colors:** no hex, `rgb()`, `rgba()` or `hsl()` value appears in `src/components/**`
  or in `globals.css`; files not yet converted sit in an explicit pending list that only shrinks.
- **Token parity:** every custom property declared in `:root` in `theme.css` is also declared in `.dark`.
- **Content integrity:** listing slugs are unique, every listing's `category` exists, and every
  `nav` and `dashboardNav` href resolves to an existing route.
- **Table helpers:** sort and filter functions for `data-table`.
- **Registry integrity:** every file path in `registry.json` exists and every
  `registryDependencies` entry names an item in the registry.

`npm run registry:build` runs as the `prebuild` script, so every build (CI, Docker, Vercel) produces the registry. `npm run build` remains the smoke test
for every page in both route groups.

## Implementation phases

1. **Restructure:** create the `mcpmarket-clone` branch on GitHub; move components into
   `ui/`, `blocks/`, `layout/`; extract `site.config.ts` and `content/`; drop routes, clone-only
   logic and `public/sites/`; add neutral brand and demo content; rewrite `AGENTS.md` and README.
2. **Theme:** split `theme.css`, add dark tokens and accent, theme script, `theme-toggle`,
   shader colors, token parity test.
3. **Dashboard:** `(dashboard)` route group, app shell and dashboard blocks, `content/dashboard.ts`.
4. **Registry:** `components.json`, `registry.json`, build script, CI step, registry test.
5. **Release:** mark the repository as a template (GitHub setting), deploy to Vercel, put the
   registry URL in README and `AGENTS.md`.

### Pull request granularity

Work lands as many small pull requests, the way the clone was built (#1–#116):

- One pull request per unit: one moved or renamed component, one new block, one route,
  one content file, one test, one config or CI change.
- Every pull request leaves `main` green: `npm run check` passes after each merge. A move
  and the import updates it causes go in the same pull request.
- Titles use conventional commits with a scope, matching history:
  `refactor(blocks): move DirectoryCard to listing-card`, `feat(dashboard): add data-table`.
- Pull requests merge in phase order; within a phase, independent ones can merge in any order.

Next.js 16 has breaking changes from earlier versions: read the relevant guide in
`node_modules/next/dist/docs/` before writing route, layout or metadata code.
